# 전주 가족여행 플래너 — 제품·기능 명세서

- 문서 버전: 0.1
- 기준일: 2026-10-09
- 제품 유형: 모바일 우선 정적 웹 애플리케이션
- 현재 구현 형태: 단일 `index.html` 중심, 서버·계정 없음

## 1. 제품 목적

성인 2명과 초등학생 자녀 1명이 전주 1박 2일 여행을 준비할 때, 방문지·시간대·이동·주차·사진을 한 화면에서 조정하고 실제 방문 전 확인사항을 관리한다. 앱의 기본 일정은 출발점이며, 현장 상황과 가족 취향에 따라 장소를 추가·제외하고 순서를 바꿀 수 있어야 한다.

### 성공 기준

1. 시간대별 일정과 이동 동선을 한눈에 확인할 수 있다.
2. 필수 방문지를 유지하면서 서로 다른 여행 페이스의 대안을 선택할 수 있다.
3. 개인이 추가한 장소와 사진을 저장하고 다음 방문에도 같은 브라우저에서 다시 불러올 수 있다.
4. 장소 운영시간·예약·주차 등 현장 확인이 필요한 항목을 실제 정보로 오인하지 않도록 명시한다.

### 범위 밖

- 예약 또는 결제 실행
- 회원가입, 서버 저장, 가족 간 실시간 동기화
- 실시간 영업시간·재고·예약 가능 여부 확인
- 실시간 교통량을 활용한 경로 최적화
- 자동으로 정확한 도보시간·주차 잔여면을 보장하는 기능

## 2. 사용자 및 사용 환경

### 주요 사용자
- 가족 여행 계획을 주도하는 보호자
- 일정의 복잡도를 줄이려는 동행 가족
- 현장에서 휴대전화로 다음 방문지와 이동 경로를 확인하는 사용자

### 사용 환경
- 스마트폰 브라우저 우선, 데스크톱에서도 확인 가능하도록 구성한다.
- 지도 타일과 지도 라이브러리는 외부 서비스에 의존하므로 지도 사용 시 인터넷 연결이 필요하다.
- 일정은 브라우저의 `localStorage`, 장소 사진 원본은 `IndexedDB` 기반으로 보관한다. 브라우저·기기 간 자동 동기화는 제공하지 않는다.

## 3. 정보 구조 및 화면 영역

### 3.1 여행 일정
- 여행 기간을 헤더에 표시한다.
- 시간순으로 방문·이동 항목을 보여준다.
- 일자별 보기와 일정 대안 선택을 제공한다.
- 일정 항목은 포함 여부와 순서를 조정할 수 있다.
- 일정 변경 후 시간대 및 표시 순서를 다시 계산한다.

### 3.2 일정 지도
- 일정에 포함된 장소를 지도에서 확인한다.
- 장소 상세에서 외부 지도 길찾기로 이동할 수 있다.
- 지도 제공자의 표기와 저작자 표시를 유지한다.
- 지도 타일·위치 데이터 오류 시에도 시간대별 일정 텍스트를 이용할 수 있어야 한다.

### 3.3 예약·방문 전 확인
- 공연, 체험, 시설 운영시간, 입장 조건 등 변동 가능한 정보를 출발 전 확인하도록 안내한다.
- 앱에 적힌 참고 정보는 실시간 확인 결과가 아니다. 공식 홈페이지·전화·현장 안내를 최종 기준으로 한다.

### 3.4 먹거리 후보 및 주차 계획
- 일정에 맞춘 음식 후보와 주차·차량 이동 관련 메모를 보여준다.
- 정보는 계획 보조 자료이며, 영업·주차 가능 상태를 보장하지 않는다.

### 3.5 장소 카탈로그 및 사용자 장소
- 기본 장소 목록에서 일정을 추가한다.
- 사용자 장소를 이름, 분류, 주소/검색어, 운영시간, 위도·경도, 예상 체류시간, 추가 사유, 메모로 등록할 수 있다.
- 사용자가 직접 사진 URL을 지정하거나 기기에서 사진 파일을 선택할 수 있다.
- 장소 생성 시 현재 일정에 곧바로 추가할 수 있는 흐름을 제공한다.
- 사용자가 등록한 장소와 사진은 명시적 삭제 또는 브라우저 저장 데이터 삭제 전까지 로컬 데이터로 유지한다.

## 4. 일정 대안 및 규칙

### 대안 정의
- **균형형**: 대표 관광과 여유를 함께 고려하는 기본 일정.
- **체험형**: 체험·공연 등의 선택 항목을 상대적으로 더 강조한다. 공연·체험은 운영 일정과 접수 가능 여부를 사전에 확인해야 한다.
- **여유형**: 체험이나 간식 등 선택 항목을 줄이고 휴식 시간을 확보한다.

### 필수 방문지 규칙
- 전동성당, 경기전, 전주난장, 전주향교를 필수 후보로 관리한다.
- 일정 대안을 변경하거나 사용자가 일정을 수정하더라도 필수 방문지의 존재와 포함 상태를 규칙으로 검사한다.
- 필수 방문지끼리 이동 순서 또는 날짜를 바꾸는 변경은 임의로 적용하지 않는다. 변경이 필요하면 사용자가 명시적으로 계획을 재구성해야 한다.
- 필수 방문지 규칙은 운영시간이나 입장 가능 여부를 보장하지 않는다. 현장 운영상 방문이 불가능하면 사용자가 일정에서 조정할 수 있어야 한다.

### 시간 계산 규칙
- 일정 항목은 예상 시작·종료 시각과 예상 체류시간을 가진다.
- 이동 항목을 별도 일정 요소로 표현한다.
- 항목 추가·제외·재정렬 후 이후 일정의 표시 시간이 재계산된다.
- 계산 결과는 계획용 예상치다. 실시간 교통·대기열은 반영하지 않는다.
- 일정은 사용자 편집을 존중하되, 중복 시각·음수 체류시간·종료가 시작보다 이른 상태를 검증한다.

## 5. 데이터 모델

| 개체 | 필수 속성 | 선택 속성/설명 |
|---|---|---|
| Plan | planId, day(s) | 균형형/체험형/여유형 식별자 |
| ScheduleItem | id, title, type, included | 장소, 이동, 체험, 휴식 등의 유형; 시작/종료, 체류시간, 설명, 위치 키 |
| Place | id, name, category | 주소/검색어, 좌표, 운영시간, 추천 체류시간, 설명, 사용자 메모, 출처/확인일 |
| PlaceAsset | placeId, assetId/blob | 사용자 사진 파일. IndexedDB에 Blob으로 저장 |
| UserPreferences | activeDay, activePlan | 화면 재진입 시 마지막 선택을 복원하는 값 |
| ScheduleOverrides | planId + day | 기본 일정에서 사용자가 수정한 일정 항목 배열 |

### 저장 경계
- `localStorage`: 현재 대안, 현재 날짜, 사용자 장소, 일정 변경 상태 등 작은 구조화 데이터.
- `IndexedDB`: 사용자 사진 Blob 등 브라우저 로컬 파일 데이터.
- 서버 전송은 구현하지 않는다. 주소·메모·사진을 외부 API로 자동 업로드하지 않는다.
- 저장 실패, 용량 제한, 브라우저 비공개 모드의 저장 제약이 있을 수 있으며 사용자에게 실패를 알린다.

## 7. 비기능 요구사항

- **사용성:** 주요 일정·지도·조작 UI가 작은 화면에서 가로 스크롤 없이 사용 가능하도록 한다.
- **복원력:** 지도 외부 의존성 오류가 일정 텍스트 열람을 막지 않도록 한다.
- **데이터 무결성:** 사용자 입력은 렌더링 전 이스케이프하고, 필수 일정 항목은 로드 시 검증한다.
- **저장 안전성:** 사진 파일을 처리할 때 지원하지 않는 파일과 과도한 크기를 검증하고, 가능한 경우 이미지 크기를 줄인다.
- **개인정보 최소화:** 서버/분석 SDK/사용자 추적 기능을 기본적으로 도입하지 않는다.
- **투명성:** 예상 체류시간과 운영 정보가 실시간 보장값이 아님을 명시한다.
- **접근성:** 버튼과 입력에 명확한 이름을 제공하고 색상만으로 선택 상태를 표현하지 않는다.

## 8. 외부 의존성

- Leaflet 1.9.4: 지도 UI 라이브러리(CDN).
- OpenStreetMap 타일: 지도 배경 및 저작자 표시.
- Google Maps URL: 외부 길찾기.
- 위 서비스의 가용성, 사용 제한, 개인정보 처리·약관 변경은 앱 운영자가 통제하지 않는다.

## 9. 오류 및 예외 처리

- 로컬 저장이 실패하면 저장 성공으로 가장하지 않고 오류 메시지를 보인다.
- 사진 DB가 열리지 않으면 일정 전체의 열람/편집은 가능한 범위에서 계속 제공하고 사진 기능 오류를 별도 처리한다.
- 좌표가 없거나 잘못된 사용자 장소는 지도 마커 생성 전에 검증한다.
- 지도 타일 로딩이 늦거나 실패하면 일정 텍스트와 길찾기 링크를 대체 경로로 이용한다.
- 예약·운영시간을 최신으로 검증하지 못했으면 '확인 완료'로 표시하지 않는다.

## 10. 보안·개인정보

- 주소, 메모, 사진을 서버로 전송하지 않는 로컬 우선 모델을 유지한다.
- 텍스트 필드는 HTML로 직접 삽입하기 전에 이스케이프한다.
- 외부 링크는 목적지를 분명히 표시한다.
- 향후 외부 API·분석 도구를 도입하면 전송 항목, 보존 기간, 동의/고지, 비밀 키 관리 정책을 별도 검토한다.

## 11. 공개 전 결정 사항

1. GitHub Pages 배포를 공식 배포 경로로 정하고 빌드/배포 성공을 검증한다.
2. 각 장소 정보의 출처와 마지막 확인일을 화면/데이터에 기록할지 결정한다.
3. 사용자 장소 수정 기능과 사진별 삭제 기능을 인수 테스트로 확인한다.
4. 두 번째 기기·다른 브라우저로 자동 동기화가 되지 않는다는 점을 UI에서 알린다.
5. 실제 현장 동선과 체류시간은 출발 전 다시 검증한다.
